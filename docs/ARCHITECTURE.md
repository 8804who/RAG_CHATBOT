# Architecture

Code-level map of the shipped system. Moved out of `CLAUDE.md` to keep it slim: read only the section for the area you touch. Design rationale (the intended end-state) lives in `RAG_ARCHITECTURE.md`, `KAFKA_INGESTION.md`, and `EMBEDDING_AND_COLLECTIONS.md`. When this doc and the code disagree, the code is the fact.

## What's built

Google OAuth login (full flow + session cookies); a `/collections` API over Qdrant (dense + sparse vectors); document **ingestion** (chunk → embed → upsert), embedding (dense via fastembed/OpenAI, sparse via BM25), a model catalog (`/models`, embedding + chat models), DB-persisted ingest/delete audit logs, and an **agentic RAG chat path** (`/chats`) — a LangChain/LangGraph tool-calling agent (not a fixed retrieve-then-generate pipeline) that can search across one or many Qdrant collections, do multi-step retrieval, and reach for a calculator/web-search/usage-stats tool, with Langfuse tracing and per-turn token-usage logging. Every frontend feature (auth, collections, documents, models, chat) now calls the real backend; there is no mock path left.

Design docs live in `docs/` (`RAG_ARCHITECTURE.md`, `EMBEDDING_AND_COLLECTIONS.md`) — read them for the intended end-state, though the shipped chat feature diverges from `RAG_ARCHITECTURE.md`'s sketch: it streams only the final answer's tokens over SSE (`POST /chats/{chat_id}/messages/stream`; the non-streaming `POST .../messages` stays) and is agent-driven rather than the single fixed retrieve→generate call the doc sketches.

## Backend

Layered, dependency-injected (FastAPI `Depends`). The chains that span multiple files:

**Auth (Google OAuth):** `api/v1/endpoints/auth/google_auth.py` → `GoogleOAuth2Service` (uses Authlib, registered in `core/oauth.py` against Google's OIDC discovery doc) → `AuthRepository` → Postgres (`User`, `GoogleSession`). On callback the service mints an opaque session token, persists a `GoogleSession`, and the endpoint sets it as the `session` cookie. Protected routes use the `get_current_user` dependency (`dependencies/auth.py`), which reads that cookie and looks up a live session.
- **Cookie-name gotcha:** Starlette's `SessionMiddleware` (holds transient OAuth state during login) is configured in `main.py` with `session_cookie="oauth_state"` specifically so it does **not** collide with the auth `session` cookie. If both used `"session"`, the middleware would clear the auth cookie on the callback response and every `/auth/me` would 401. Keep these two names distinct.

**Vector store:** `api/v1/endpoints/collections.py` → `QdrantService` → `QdrantRepository` → `clients/QdrantDBClient` (wraps `AsyncQdrantClient`). `CreateQdrantCollectionRequest` carries dense/sparse vector configs that the repository translates into `qdrant_client.models` types. On create, `QdrantService` validates the requested embedding model+dimension against the registry, then persists a `CollectionMeta` row (Postgres) pinning that collection to one embedding model/dimension — because **all vectors in a collection must share the same model**. `get_collection`/`delete_collection` read and clean up that row alongside Qdrant.

**Embedding & ingestion (RAG write path):** `api/v1/endpoints/documents.py` → `DocumentService` (`services/ingestion/`) orchestrates ingest: load the collection's `CollectionMeta` to pick the embedding model → `chunk_text` (`utils/chunker.py`, word-window + overlap) → `EmbeddingService.embed_documents` → `QdrantRepository.upsert_points`. Every ingest/delete is wrapped so success **and** failure are written to `DocumentManageLog` (Postgres) via `LogRepository` (who/when/what). A "document" is virtual: chunks share a `document_id` in their Qdrant payload, and list/get/delete group by it (there is no per-document table in Qdrant).
- **Embedding layer:** `EmbeddingService` combines a dense client + a sparse encoder. Dense clients (`clients/embedding/`, `EmbeddingClient` interface) cover fastembed (local) and OpenAI; `EmbeddingModelRegistry` (`services/model_registry.py`) is a catalog mapping a public model name → `(info, client)`, built from `core/model_config/embedding_model_config.py` and surfaced at `GET /models`. Sparse is BM25 (`BM25SparseEncoder`, `SparseEncoder` interface), created once as a singleton and warmed in `lifespan`. A collection gets sparse vectors only if it was created with a sparse config; ingest keys off `with_sparse`.

**Chat & retrieval (agentic RAG read path):** `api/v1/endpoints/chats.py` (`POST /chats`, `POST /chats/{chat_id}/messages`, `POST /chats/{chat_id}/messages/stream`, `GET /chats/{chat_id}/messages`) → `AgentChatOrchestrator` (`services/agent/agent_orchestrator.py`), composing `ChatRepository` (Postgres `Chat`/`ChatMessage`), `CollectionMetadataRepository`, `RetrievalService`, `UsageStatsService`, `LogRepository`, `RedisClient`, `AsyncSessionLocal` (session factory for tools), and an optional Langfuse `CallbackHandler`. `POST /chats` validates the chat model against `ChatModelRegistry`; `collection_name` is **optional** — if given, it's validated against `CollectionMeta` and pinned for the chat's lifetime (legacy single-collection mode, frontend locks its picker on this); if omitted, the agent picks collection(s) per query. `GET .../messages` (owner only) returns `chat_model`, `collection_name` and the `chat_messages` rows ordered by `(created_at, id)`. `send_message` runs: load chat → ownership check (403 `ChatAccessDeniedError`, an explicit IDOR guard) → `db.commit()` to end the request session's read transaction (so no pooled connection sits idle-in-transaction through the LLM loop) → per-chat Redis lock `SET chat:turn-lock:{chat_id} NX EX CHAT_TURN_LOCK_TTL_SECONDS` (409 `ChatTurnInProgressError` if held; deleted in `finally`) → build tools that each open their own short session per call → `create_agent(...)` → read the thread's pre-turn messages (`aget_state`) → `graph.ainvoke(...)` with **only the current query**, `thread_id = chat_id`, `durability="exit"`, inside `asyncio.timeout(CHAT_TURN_TIMEOUT_SECONDS)` (lock TTL = timeout + 60 s) → this turn's messages = those whose id wasn't in the pre-turn state (survives a mid-turn summary) → answer, citations, tool calls from them; tokens from a run-level `UsageMetadataCallbackHandler` (so summarizer calls are counted) → one transaction storing the user + assistant `chat_messages` rows (`add_turn_messages`) → usage + tool-call logs → `checkpointer.aprune([chat_id], strategy="keep_latest")` (best-effort, warning on failure). **A turn is all-or-nothing (D-016):** on any agent error the thread is reset to the pre-turn messages via `aupdate_state({"messages": [RemoveMessage(REMOVE_ALL_MESSAGES), *before]})` and nothing is written to `chat_messages`; `durability="exit"` alone does not prevent this, LangGraph still saves the last step's state (e.g. an `AIMessage` with unanswered `tool_calls`) when the run raises. Tokens spent in failed turns are not in the usage log (Langfuse only). **Streaming (`stream_message`, D-018):** the same ownership check + lock run before the endpoint returns, so 403/404/409/422 stay JSON; it then returns a `StreamingResponse` over an async generator that owns the lock and deletes it in its own `finally` (if the client drops before the first chunk the generator never starts and the lock waits out its TTL). The generator runs `graph.astream(..., stream_mode="messages", durability="exit")`, emits `token` for non-empty text chunks whose `metadata["langgraph_node"] == "model"` (summarizer and tool output are skipped; text the model writes before a tool call is streamed too, and `done` replaces it), then reads the final thread via `aget_state` and runs the same persistence as `send_message` (`_finish_turn`) before one `done`. Any failure, including persistence, closes the astream, rolls the thread back and ends with one `error` (`AppException.message`, otherwise the generic message). Cancellation or a disconnect closes it the same way and re-raises. `CHAT_TURN_TIMEOUT_SECONDS` is a deadline on each graph/state await (time blocked writing to the client is not counted). The request `db` session stays open while the body streams.
- **Multi-turn memory:** the agent is built with a LangGraph `AsyncPostgresSaver` checkpointer (`dependencies/clients.py::get_checkpointer`, a psycopg pool built from `checkpointer_conninfo()` (key=value, so special characters in the password are safe), opened + `setup()` in `main.py` lifespan) and `SummarizationMiddleware`. The checkpointer restores the chat's whole agent state (past questions, answers, *and* tool calls/results) per `thread_id = chat_id`; once that state passes `CHAT_SUMMARY_TRIGGER_TOKENS` (30000) the middleware replaces older messages with one summary `HumanMessage` written by `CHAT_SUMMARY_MODEL` (`gpt-4o-mini`), keeping the last `CHAT_SUMMARY_KEEP_MESSAGES`. Gotchas: checkpoint tables (`checkpoints`, `checkpoint_writes`, `checkpoint_blobs`, `checkpoint_migrations`) are created by `setup()`, **not Alembic** — don't let autogenerate drop them; `chat_messages` is the user-visible transcript and checkpoints are only agent memory (D-016), so history is stored twice; summarizer tokens are summed into the chat model's usage row (priced at the chat model's rate); `aprune` is not implemented by `InMemorySaver` (tests only).
- **Chat model limits:** every `ChatOpenAI` in `core/model_config/chat_model_config.py` gets `max_tokens=DEFAULT_CHAT_MAX_COMPLETION_TOKENS`, `timeout=CHAT_MODEL_TIMEOUT_SECONDS`, `max_retries=CHAT_MODEL_MAX_RETRIES`.
- **Tools** (`services/agent/tools.py`, one factory per tool, built fresh per request): `build_retrieval_tool` reuses `RetrievalService.retrieve` unchanged — if the chat has a pinned collection the tool takes only `query`; otherwise it lists every `CollectionMeta` row (name + `description`) into the tool's description and takes `collection_name` too, letting the model choose (and re-query, possibly against a different collection, since nothing stops it calling the tool again — this is what makes retrieval multi-step). `build_calculator_tool` evaluates arithmetic via `simpleeval` — deliberately **not** a code-exec/Python-REPL tool, since that would be unsandboxed remote code execution reachable from a chat prompt. `build_retrieval_tool`/`build_usage_stats_tool` take an `async_sessionmaker` and open one session per call, because parallel tool calls from `ToolNode` would otherwise share one `AsyncSession` concurrently. `build_usage_stats_tool` wraps the existing `UsageStatsService.get_user_stats`, hard-scoped to the calling `requester_id` with no user-controlled query surface — deliberately not a free-form SQL tool, since an LLM-written query against the shared Postgres instance (which also holds `users`/`google_sessions`/other users' `chats`) would be a real data-exposure/injection risk with no sandboxing here. `build_web_search_tool` returns `None` (tool omitted) unless `TAVILY_API_KEY` is set.
- **Citations:** the retrieval tool returns its results as a JSON string in `ToolMessage.content` (LangChain's own tool-output stringification does this for any dict return, confirmed against the installed `langchain-core`); after the run, `_extract_citations` re-parses every `search_documents`/`tavily_search` `ToolMessage` by name and dedupes by `chunk_id`/`url`. This was chosen over LangChain's tool-`artifact` pass-through (`response_format="content_and_artifact"`), which has had open compatibility gaps in prebuilt agent graphs — parsing the same JSON the model reads is simpler and doesn't depend on that plumbing. `Citation` (`schemes/dto/chat.py`) has a `source_type` (`"document"` | `"web"`) plus the fields relevant to that type (`chunk_id`/`document_id`/`collection_name` vs `url`).
- **Retrieval (unchanged):** `RetrievalService` embeds the query with the collection's *pinned* embedding model (`CollectionMeta.embedding_model` — same invariant ingestion enforces) via `EmbeddingService.embed_query`, then calls `QdrantRepository.search`. It queries hybrid when the live Qdrant collection has a sparse vector configured (checked against Qdrant at query time via `get_collection`, not stored in Postgres): two `Prefetch` queries (dense + sparse) fused server-side with RRF (`models.FusionQuery(fusion=models.Fusion.RRF)`); dense-only otherwise.
- **Chat model catalog:** `ChatModelRegistry` (`services/model_registry.py`) now holds `(RegisteredChatModel, BaseChatModel)` tuples — `core/model_config/chat_model_config.py` builds `langchain_openai.ChatOpenAI` instances (not the old hand-rolled `LLMClient`) at import time, so `OPENAI_API_KEY` unset still crashes the server on boot the same way it always did.
- **Pricing:** `core/model_config/pricing_config.py` carries both `kind="embedding"` and `kind="chat"` rows in one flat list. Each row's `model` string must match its catalog key (`embedding_model_config.py` / `chat_model_config.py`) exactly — nothing enforces this, a mismatch just makes `UsageStatsService` silently report `cost=None` for that model.

**Clients layer:** `clients/` wraps external services (Qdrant async client, Redis) as classes; `dependencies/clients.py` exposes them as `@lru_cache` singletons; `main.py`'s `lifespan` warms them on startup and closes them on shutdown.

**Middleware:** `middlewares/ApiCallLogMiddleware` logs every API call (one `logger.info`/`warning` line — not a DB table) with `api_call_id`/`user_id`/`api`/`status_code`/`process_status`/`call_time`/`end_time`/`duration_ms`. It resolves `user_id` itself straight from the session cookie (independent of the `get_current_user` dependency) so it can log public/unauthenticated calls too, best-effort (`None` if no valid session) rather than 401ing. **Registration order matters and is counter-intuitive:** Starlette's `add_middleware` *prepends* to the middleware list, so the middleware added *last* ends up *outermost* — `ApiCallLogMiddleware` is therefore registered after `CORSMiddleware`/`SessionMiddleware` in `main.py`, not before, so it wraps the full request lifecycle and sees the final status code after exception handlers have already translated it. `/health` and `/` are excluded (`core/constants.py::API_CALL_LOG_EXCLUDED_PATHS`).
- **Request-correlated logging:** the middleware stores its `api_call_id` in a contextvar (`core/request_context.py::api_call_id_var`) for the lifetime of the request; `core/logging_config.py`'s handler-level filter injects it into **every** log line (`[api_call_id=...]` prefix), regardless of layer — service/repository code never touches this value directly, it just logs as usual and the id shows up automatically. This is what makes `grep api_call_id=<id>` across services show the full story of one request, from its business-event logs down to whatever failed. Outside a request (worker processes) it prints as `-`; workers keep using `document_id` as their own correlation key.

**DB:** fully async SQLAlchemy (asyncpg). `dependencies/db.py` holds the engine + `async_sessionmaker`; `get_db_session()` yields an `AsyncSession`. Schema is managed by Alembic (`backend/app/migrations/`, run `uv run alembic upgrade head` before starting the server) — `migrations/versions/` is gitignored, so each environment's migration history is local; regenerate the baseline with `uv run alembic revision --autogenerate` if a DB is ever wiped.

**Config:** `core/config.py` — `Config` (pydantic-settings) loads everything from env into a module-level `config` singleton imported everywhere. Required: `POSTGRES_*`, `REDIS_*`, `QDRANT_URL`, `GOOGLE_CLIENT_*`, `SESSION_SECRET`. `OPENAI_API_KEY` is typed as optional but is now effectively required at startup: `core/model_config/chat_model_config.py` builds `ChatOpenAI`s at **import time**, and it raises immediately if no key is available — an unset key crashes the whole server on boot, not just the OpenAI-backed embedding models (fastembed models still run locally, no key needed). `TAVILY_API_KEY`/`LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY`/`LANGFUSE_BASE_URL` are optional and gate the agent's web-search tool / Langfuse tracing respectively (both silently disabled, not an error, when unset) — since `langchain-tavily`/`langfuse` read these from `os.environ` directly rather than accepting them as constructor args, `config.py` re-exposes whatever Config loaded back into `os.environ` via `setdefault`, the same pattern already used for `FASTEMBED_CACHE_PATH`.

**Constants:** `core/constants.py` holds shared magic numbers/hardcoded strings (chunking defaults, log status strings, default currency, etc.) — declare new cross-cutting constants there rather than inlining literals. Domain enums that are tightly coupled to one model (`DocumentStatus`, `DocumentOperation`) stay co-located with that model; `core/constants.py` is for values with no natural single owner.

### Import convention

The import root is `backend/app`, not the repo root. Imports are root-relative (`from core.config import config`, `from repositories.vector_db import QdrantRepository`). Always run/test backend code with `backend/app` as the working directory.

### Ingest workers

The API server only produces to Kafka; it never consumes. Without the three workers
running, uploads stay stuck at `UPLOADED` forever and no ingest audit log is ever
written (see `docs/KAFKA_INGESTION.md` / `RAG_ARCHITECTURE.md` §5 for the pipeline).

## Frontend

- **Same-origin via proxy:** `vite.config.ts` proxies `/api` → `http://localhost:8000`, so the SPA and API share an origin in dev and session cookies "just work." `API_BASE` is empty by default (`src/lib/config.ts`).
- **No more mocks:** every feature (auth, collections, documents, models, chat) calls the real backend. `mockStore.ts` was deleted; `USE_MOCKS`/`delay` (`src/lib/config.ts`) are unused leftovers — nothing reads them anymore. `chat.ts` `streamMessage` POSTs to `/chats/{id}/messages/stream` and reads the SSE body incrementally (fetch + `ReadableStream`, parser in `src/lib/api/sse.ts`; EventSource can't POST): `token` deltas render a live assistant bubble, the `done` payload replaces them as the authoritative answer, and an `error` event or a stream ending without `done` rejects with `ApiError` (nothing is saved, so Retry resends). `useChat`'s AbortController cancels the stream. `CreateChatRequest.collection_name` is optional — omit it (the "Let the agent choose" option in `ChatPage.tsx`) to let the agent pick collection(s) per query instead of pinning one at chat creation.
- **API access:** all calls go through `apiFetch` (`src/lib/api/client.ts`, sends `credentials: 'include'`) and the typed wrappers in `src/lib/api/`. Server state is managed with React Query (one `use*` hook module per feature under `src/hooks/`); `src/auth/AuthContext.tsx` + `components/ProtectedRoute.tsx` gate authenticated routes (`/chat`, `/documents`, `/collections`) behind a shared `Layout`.

## Configuration

Secrets live in git-ignored env files. The backend reads `backend/app/.env` (see `SettingsConfigDict`); compose reads `docker.env` at the repo root. No committed `.env.example`. Optional agent-related vars (all silently disable the corresponding feature when unset, never an error): `TAVILY_API_KEY` (web-search tool), `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY`/`LANGFUSE_BASE_URL` (agent run tracing). `LOG_INFRA_ENDPOINTS` (default `false`): when `true`, `/health`, `/metrics` and `/` are logged in the API call log and uvicorn access log.

## Run in Docker

`system-docker-compose.yaml` (project `rag_chatbot_system`) holds infra only. `service-docker-compose.yaml` (project `rag_chatbot_service`) runs `api` (:8000, runs `alembic upgrade head` first), `frontend` (nginx-unprivileged, host :5173 → :8080) and `ingest-worker` on the external `rag_chatbot_system_default` network, so start infra first: `docker compose -f system-docker-compose.yaml up -d && docker compose -f service-docker-compose.yaml up -d --build`. The backend image (`backend/app/WorkerImage.Dockerfile`) runs as UID 10001 with root-owned, read-only app files; only `/cache/fastembed` (volume `rag_chatbot_service_fastembed_cache`) is writable. Both containers read `backend/app/.env` and override the infra hosts to the compose service names. The old `rag_chatbot_fastembed_cache` volume is unused and can be removed by hand.

## Monitoring

Optional local stack in `monitoring-docker-compose.yaml` (project `rag_chatbot_monitoring`, config in `monitoring/`). It joins the infra stack's `rag_chatbot_system_default` network, so start the infra stack first: `docker compose -f system-docker-compose.yaml up -d && docker compose -f monitoring-docker-compose.yaml up -d`.
- Prometheus http://localhost:9090 (7d retention), Grafana http://localhost:3000 (Prometheus datasource provisioned). Exporters (postgres, redis, kafka, cadvisor, node-exporter) are internal only; Qdrant is scraped directly with its API key from `docker.env`.
- Remote server: all published ports bind every interface (Prometheus and Grafana included), so other machines reach them at `<server>:<port>`. Prometheus has no auth; set `GF_SECURITY_ADMIN_PASSWORD` in `docker.env`, and firewall the infra ports (Postgres, Redis, Qdrant, Kafka, Kafka UI, RedisInsight) to trusted IPs. For external Kafka clients start infra with `KAFKA_ADVERTISED_HOST=<server IP or DNS>` (default `localhost`). For the app, set `FRONTEND_URL` and `GOOGLE_REDIRECT_URI` in `backend/app/.env` to the server address and register that redirect URI in Google Cloud.
- Logs: Alloy (`monitoring/alloy/config.alloy`, Docker socket) ships container stdout to Loki (7d, no host port); query in Grafana Explore → Loki by `container` / `compose_service`. The host-run API's logs are not collected until it is containerized.
- The API exposes Prometheus metrics at root `/metrics` (`prometheus-fastapi-instrumentator`, wired in `main.py`; not under `/api`, `/health`, `/metrics` and `/` are left out of both the API call log and the uvicorn access log unless `LOG_INFRA_ENDPOINTS=true`): `http_requests_total`, `http_request_duration_seconds`, `http_requests_inprogress`, labelled by route template and status class. The `api` job scrapes `host.docker.internal:8000`.
